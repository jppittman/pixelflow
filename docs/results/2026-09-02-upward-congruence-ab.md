# Upward congruence closure: A/B (issue #1106)

`Congruence::Upward` vs production's `Congruence::Downward`, both through `Optimizer::production()` — same rule set, same `Budget::Production`, same `CostModel::latency_prior()`. 406 kernels (206 real + 200 synthetic), plus 206 numeric-first rows for the order-sensitivity question.

## Verdict

**Upward congruence closure works, is not worth shipping, and refutes the
hypothesis it was built to test.** `PRODUCTION_CONGRUENCE` stays
`Congruence::Downward`; the implementation ships behind
`Optimizer::congruence()` so the arm stays runnable.

Three findings, in descending order of how much they should change what the
program does next:

1. **It makes rule order matter MORE, not less.** This was the headline
   question — if the order effect in #1101/#1088 were substantially an
   artifact of missing congruence, closing congruence should pull the two
   orderings together. It does the opposite: mean absolute deviation of the
   numeric-first/production cost ratio moves **0.0309 → 0.0535 (+73%)** on the
   111 distinct real kernels, and the number of kernels where order changes
   the extracted cost at all moves 158 → 188. So #1101 and #1088 do **not**
   need reframing: the order effect is not congruence-completeness wearing a
   disguise. If anything, a more completely closed graph gives rule order
   *more* room to matter, because there are more equal terms for the extractor
   to choose badly among.

2. **It does not touch the class cap.** 231/406 kernels hit `ClassCap` in both
   arms — the same 231, with the same typed stop reason on every single
   kernel. Pooled *live* classes go **up** 0.77%. This is the online
   confirmation of the offline probe's corrected H-a analysis
   (`2026-09-02-missing-congruence.md`): the cap binds on genuine e-graph
   growth from rule application, not on unrecognized duplicates. Closure
   changes *what* the graph holds at the cap, not how fast it gets there.

3. **On extraction quality it is a wash that redistributes.** Pooled real-kernel
   cost moves −0.07% — nothing — but underneath, 36 of 111 distinct real
   kernels get **worse** (up to +17.3%) and 28 get better (down to −14.6%).

### Why more congruence makes extraction worse

This is not a bug in the closure, and it is worth stating plainly because it
points at where the real headroom is. `extract_dag` is explicitly **not** an
argmin under the cost model — `Optimizer::cost`'s own doc comment says so: it
sums children, which prices a tree rather than a DAG; it is a single DFS, so
on the cyclic graphs saturation always produces, a class whose child is still
on the stack is scored at a cycle sentinel and never revisited.

A greedy heuristic with that shape has no monotonicity guarantee in the size
of an e-class. Merging strictly more terms into a class gives the DFS more
nodes to pick among and more opportunities to hit the cycle sentinel, so a
*better* graph can yield a *worse* extraction. That is exactly the observed
signature: the equalities are strictly a superset (law L2), the pooled cost is
flat, and the per-kernel outcomes scatter both ways.

**The consequence for the research program:** congruence completeness is not
the bottleneck — extraction is. Upward closure is a prerequisite whose value
is gated behind an extractor that can actually exploit a larger class, which
is what the `Reranker` seam exists for. Re-running this A/B with a reranked or
argmin extractor is the experiment that would make this change pay; until
then, shipping it buys a 1.5-edge-per-class memory tax and ~6.5 extra owner
repairs per union to move pooled cost by −0.07% and make 36 real kernels
worse.

### What was ruled out

The regressions are not an artifact of this implementation. `repair_class`
has a pre-existing writeback bug — when a mid-loop `union` picks the *other*
class as survivor, the repaired nodes are written back to the merged-away slot
and become unreachable — and upward repair triggers many more such unions, so
it was the obvious confound. Patching the writeback to `self.find(id)` and
re-running the whole A/B moved the result to 73 real kernels worse / 56 better
(from 72 / 68): the same picture. The bug is real and referred separately; it
is not what produces these regressions.

### Caveats

- `glyph32` duplicates `glyph16` structurally (see below), so the 406-kernel
  tables over-weight glyphs ~2×. The 111-distinct-kernel section is the honest
  real-kernel headline.
- Wall clock is **context, not a metric**: the machine was shared and loaded
  (load average 4.7–5.0 across these runs). Every metric that decides anything
  here — cost, class counts, applications, stop reason — is deterministic
  under `CostModel::latency_prior()` and independent of load.
